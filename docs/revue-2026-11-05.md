# Revue du dépôt — 2026-11-05

Lecture du code et des manifestes après la phase 1 (T0.2–T1.27), complétée jusqu'à la v0.1.3
(2026-11-09). Les points marqués comme bugs ont été constatés dans le code, pas reproduits par
exécution, sauf mention contraire. Cocher une case quand le point est traité (et citer la PR).

Les points ouverts sont classés par priorité ; le repère entre crochets (`[1a]`, `[5.1]`…) est
celui des versions précédentes de cette revue, cité dans les PR. Les points traités sont
archivés à la fin, avec leur texte d'origine.

| Priorité | Sens |
| --- | --- |
| **P0** | Bloquant : à trancher avant la prochaine version. |
| **P1** | Haute : visible par les utilisateurs, ou suivi du projet faux. |

| **P3** | Basse : confort, finition, micro-optimisation. |

## P0 — Bloquant

- [ ] **T0.1 — le nom du projet** `[7.2]` `[3]`. Trois signaux : la politique de Canonical vise

## Ce qui est bien fait

- Discipline des lints : `forbid(unsafe)`, refus de `unwrap` / `expect`.
- Erreurs typées et normalisées, vérifiées par snapshots `insta`.
- Kit de conformité commun aux fournisseurs.
- `openapi.json` et référence de configuration générés puis vérifiés par diff en CI.
- Journal non bloquant (`try_send`).
- Fournisseurs sans I/O, donc testables isolément.
- Release automatisée de bout en bout (v0.1.3) : binaires, image multi-arch signée, lanceur npm
  publié sans jeton avec provenance.

### [1] Problèmes réels

- [x] **1a. API d'administration sans authentification.** `buntu-security` n'est utilisé que
  par des tests ; les routes `/admin/v1/*` sont ouvertes
  ([lib.rs](../crates/buntu-gateway/src/lib.rs)) et l'écoute par défaut est `0.0.0.0:8080`
  ([main.rs](../crates/buntu-cli/src/main.rs)). N'importe qui sur le réseau peut ajouter un
  fournisseur, rediriger une route ou lire le journal, alors que T1.20 est marquée « fait ».
  - [x] Middleware axum d'authentification sur le sous-routeur `/admin`.
  - [x] Écoute par défaut sur `127.0.0.1`.
- [x] **1b. Le journal des requêtes cesse d'écrire après un redémarrage.** `request_id()`
  produit `req-1`, `req-2`… à partir d'un compteur remis à 1 à chaque démarrage
  ([state.rs](../crates/buntu-gateway/src/state.rs)), or `request_log.id` est une
  `PRIMARY KEY`. Après un redémarrage, chaque `INSERT` échoue ; `StoreSink` s'arrête à la
  première erreur (`?`) et le lot entier est perdu, en silence (seul un compteur le signale).
  - [x] Identifiant unique (aléatoire via `fastrand`, déjà présent, ou horodaté).
  - [x] Insertion du lot dans une seule transaction.
- [x] **1c. Le budget de réessais ne limite rien.** `FallbackChain::default()` est recréée à
  chaque requête ([chat.rs](../crates/buntu-gateway/src/routes/openai/chat.rs)), donc
  `RetryBudget` repart plein (20 jetons) à chaque fois. La preuve de T1.5 (≈ 20 %) ne vaut que
  dans le test. Correctif : une seule chaîne (ou un seul budget) dans `GatewayState`.
- [x] **1d. Erreur en cours de flux présentée comme un succès.** La boucle
  `while let Some(Ok(frame))` s'arrête en silence si la connexion amont casse, puis envoie
  `data: [DONE]`.
  - [x] Émettre un événement d'erreur sur `Some(Err(_))` dans `routes/openai/chat.rs`.
  - [x] Même correction dans `routes/anthropic/messages.rs`.
- [x] **1e. Aucun timeout sur les vrais appels amont.** `TimedExecutor`, `pipeline` et
  `hooks` ne sont utilisés que dans `buntu-core/tests/*`. Un fournisseur muet bloque la
  requête indéfiniment.
  - [x] Brancher `TimedExecutor` dans la passerelle.
  - [x] Plafonner la taille des corps de réponse amont (`collect()` dans
    [upstream.rs](../crates/buntu-gateway/src/upstream.rs), y compris la lecture du corps
    d'erreur dans `open_stream`).
- [x] **1f. Pas de TLS amont.** Les URL `https://` sont refusées
  ([upstream.rs](../crates/buntu-gateway/src/upstream.rs)) : OpenAI, Anthropic et Gemini sont
  inaccessibles en conditions réelles. Le message renvoie à T1.21, marquée « faite ». À
  traiter, ou à inscrire en réserve visible dans `docs/status.md`.

### [2] Une seule source de vérité

- [x] **Trois sources de configuration qui divergent** : le fichier TOML (rechargé à chaud),
  `AdminStore` en mémoire (API admin) et les tables `providers` / `provider_keys` / `routes`
  de SQLite (jamais lues par la passerelle). Un rechargement du fichier efface les
  modifications faites par l'API. Choisir une seule source et l'écrire dans une ADR.
- [x] **Type de fournisseur en chaîne libre**, répété dans le registre
  ([registry.rs](../crates/buntu-gateway/src/registry.rs)), dans `authorize()`
  ([executor.rs](../crates/buntu-gateway/src/executor.rs)) et non vérifié par la validation :
  `type = "opnai"` passe `config validate` puis donne une 500 à l'exécution.
  - [x] La validation vérifie le type contre la liste des fournisseurs connus.
  - [x] L'en-tête d'authentification devient une méthode du trait `Provider`.
- [x] **Doublons dans `executor.rs`** : `prepare` / `prepare_embeddings` quasi identiques ;
  bloc « statut non 2xx → `map_error` + pause de clé » copié trois fois.
- [x] **Doublons dans les routes** : boucle de repli des flux et émission SSE copiées entre
  `chat.rs` et `anthropic/messages.rs` ; calcul d'horodatage `SystemTime::now()` répété.
- [x] **Journal incomplet** : seules les réponses 200 de `/v1/chat/completions` sont
  journalisées (pas les erreurs, les flux, les embeddings ni `/anthropic`). Une fonction
  commune appelée en sortie de route couvrirait tout.
- [x] **Deux routeurs de santé** : `app()` (« tests historiques ») duplique celui de
  `app_with_state`. Basculer les tests sur `app_with_state` et supprimer `app()`.
